# Magnum onboarding UX audit and redesign proposal

Status: audit/design only; implementation requires Owner review. Evidence collected
against the current application in isolated Phoenix/Vite/Keycloak/PostgreSQL fixtures,
not the Owner's personal company. No production behavior or development data changed.

## Executive summary — five priorities

1. **P0: no reachable finish in Setup.** Review warns that drafts are unapplied, but
   supplies no final-review action or clear outcome. The backend supports final review
   states; this UI does not expose them. A finished draft is not a published business.
2. **P1: progress has two competing meanings.** Tabs change the editor while the saved
   state and bottom “Validate … and continue” action can refer to a different stage.
   Owners cannot reliably tell whether they advanced, merely viewed, or saved a step.
3. **P1: repeated handoffs obscure the next task.** Platform → identity → business form
   → success → ordinary login → Admin → Resume Setup → Begin setup → Configure shop
   creates avoidable decision points. The security boundaries are necessary; the
   explanatory and navigation burden is not.
4. **P1: business configuration reads like an internal data editor.** “IANA timezone,”
   defaults/overrides, dispatch keys, classifications/responsibilities/access requests
   and revision numbers compete with the customer's immediate task.
5. **P1: form density and weak local recovery undermine confidence.** An always-visible
   guide, nested fieldsets, extensive role controls and long generic save errors make
   mobile work especially slow. Explicit save controls live after the entire editor.

Severity: P0 blocks completion of the intended task; P1 substantially increases
confusion or work; P2 affects polish. These are UX findings, not claims of auth defects.

## Current journey and actual capabilities

| Route / handoff | Implemented behavior | Important limit |
|---|---|---|
| `/platform` | SaaS landing; create-business and sign-in links | Names Keycloak and explains tenant mechanics before user benefit |
| `/signup` | Account choices, proof-gated business/shop form, review, confirmed success | A successful signup creates actual business/shop/Owner records, not a live website |
| `/auth/signup/login` → Keycloak | Signup-purpose OIDC; new registration, email verification, existing-account SSO | Realm registration and SMTP must be ready; isolated success alone does not prove local readiness |
| `/auth/callback` → `/signup` | Browser-bound verified proof; returns to form or failure | Proof expires; not an ordinary session |
| `/auth/signup/business` | Atomic provisioning; duplicate-safe receipt | Browser cannot select an existing tenant or arbitrary Owner |
| `/auth/login` → callback → `/admin` | Ordinary session; authorized business/shop selection | Pending-account denial and current RBAC remain authoritative |
| `/admin` | Real dashboard, Employees, Calendar and Owner Resume Setup | Management visibility depends on selected business and backend capability |
| `/setup/:businessId` | Dedicated authorized Setup layout with business selector | Not the daily-operations Admin navigation |
| Begin setup / Business tab | Creates or retrieves private draft; lists already-provisioned shops | Configure shop adds its reference to a proposal; does not create that shop again |
| Locations | Shared defaults, per-location proposals, mobile coverage/dispatch/buffer drafts | No travel-aware booking or capacity activation |
| Staff | Proposed people, employment classification, assignments, responsibilities and access requests | No hiring, invitations, accounts, memberships or grants are applied |
| Services | Custom vehicle categories, services, duration, price matrix, shop overrides | No active catalog or customer-price changes |
| Branding | Three presets, colors, text, sample website preview | Placeholder logo; no upload, publishing, domain or real availability |
| Guided assistant | Deterministic topic/proposal/approval/history | Not AI; proposes current editor data, not natural-language generation |
| Review | Summaries and preview; saved-state display | No UI finish/publish action; completed-state behavior is not a reachable end-to-end UI journey |
| `/`, `/services`, `/contact` | Separate Magnum Detailing public website and booking | Not a tenant website generated by onboarding |

Typical successful registration requires choosing identity entry, submitting Keycloak
registration, following the verification email, completing password requirements,
filling business/shop details, reviewing, creating, acknowledging success, ordinary
sign-in, Resume Setup, Begin setup and Configure shop. Existing-account SSO skips
credential entry where appropriate; exact clicks depend on Keycloak required actions.

| ID | Severity | Current problem / evidence state | Proposed response |
|---|---|---|---|
| F01 | P0 | Setup Review has no finish action (`review` captures; source SetupWorkspace) | “Save setup review” only after backend validation; explicitly state that publication is unavailable. Never rename it Publish |
| F02 | P1 | Tab navigation and saved workflow progress diverge (`overview`, `locations`, `review`) | One stepper driven by saved backend state; distinguish viewed, edited, saved and validated. Tie primary action to visible step |
| F03 | P1 | New first shop must be manually selected again using Configure (`begin-setup-empty`, `golden-new-setup`) | Present the existing first-shop reference as the first location editor; save through the existing draft API, never create a duplicate shop |
| F04 | P1 | Generic error lists staff, branding, catalog and locations regardless of failing field (`validation`) | Summary at top + field-level messages where API supports them. Focus first invalid field. If backend lacks paths, show an honest stage-level error; no invented precise cause |
| F05 | P1 | Guided assistant is placed before every manual editor (`proposal`, `locations`, `staff`) | Optional collapsed “Guided help” panel; manual setup is primary. Human-readable change diff, not raw proposal JSON |
| F06 | P1 | URLs are described as “Booking website address” though no site is published (`business-and-first-shop-form`, help) | “Business address identifier” with a short example and explicit reservation notice; generate defaults, hide shop identifier under Advanced, preserve manual edits |
| F07 | P1 | Locations starts with shared defaults and mobile fields before a concrete location (`locations`) | Lead with location cards; In-shop / Mobile / Both selection. Reveal mobile drafts only when relevant; move shared defaults and overrides under Advanced |
| F08 | P1 | Staff repeats employment, responsibility and access concepts in deeply nested boxes (`staff`) | Ask job classification and work locations first; optional collapsed “Proposed app access.” Preserve separate data and review; never infer RBAC from classification |
| F09 | P1 | Services exposes categories, proposals and per-shop overrides together (`services`) | Simple service rows, price matrix and optional shop customization drawer. Explain “Vehicle sizes” with custom business-owned labels |
| F10 | P1 | Review is a text-heavy summary rather than a resolution checklist (`review`, branding preview) | Section cards with Edit, missing requirements, saved/deferred state and explicit unpublished outcome |

| F14 | P1 | Signup success requires deliberate ordinary login but does not carry an obvious next-business task | Keep success persistent. Explain why sign-in follows; after authorized context loads, offer the newly created business's Setup. Never accept an arbitrary return URL |

## Proposed cohesive journey

Identity remains before provisioning; the visual wizard must not pretend drafts
exist before the required proof and atomic business creation. Group the experience:

**Account → Your Business → First Location → Confirm creation → ordinary login →
Services & Pricing → Your Team → Branding → Review & Finish setup review.**

After creation, show the same business/location information as saved operational
facts with separate editable proposals. Additional locations remain draft-only.
The initial shop name/timezone gathered during creation is reused, not requested twice.

| Step | Main interaction | Safe optional/deferred behavior |
|---|---|---|
| Account | Two clear choices; explain password and email handoff without implementation jargon | No bypass of verification; local Mailpit instructions belong in development documentation |
| Your Business | Name; suggested unique identifier with help; explain tenant creation | Identifier editable before provisioning; conflicts preserve safe inputs |
| First Location | Name, searchable timezone; physical address and operating-mode proposal | Additional locations later; mobile settings explicitly planning-only |
| Services & Pricing | Business-defined vehicle sizes, service cards, durations and price matrix | “Configure later” only if backend accepts current state. Deferred is not Complete |
| Your Team | “Just me” or proposed staff; location selection; optional access requests | Zero staff is valid. No invitations or access are sent/restored |
| Branding | Preset cards, colors and contacts; clearly marked illustrative preview | Allow Save & exit; do not label required fields optional or mark skipped branding validated |
| Review | Saved summary, missing requirements, Edit links, truthful next steps | Finish only a draft review through supported confirmation; publication stays unavailable |

### Layout and interaction model

Desktop 1440: restrained existing dark Admin theme; compact business identity header;
left stepper (~220px), bounded editor (~760px), optional contextual help. One primary
bottom action. Review uses two-column section cards; guide is opt-in, not a second
workflow above the page.

Tablet 768: horizontal or collapsible step overview, single editor column, secondary
help disclosure. Preserve visible business identity and saved state. Avoid three
competing navigation rows.

Mobile 390: “Step n of 6 · Locations” button opens an accessible step list; one-column
editor; collapsed summaries for additional locations/staff/services; sticky primary
action with secondary Back. Preview opens an explicitly labeled mode and restores
editor focus. No horizontal document scrolling; action area must not obscure fields.

Errors: retain safe inputs; show specific field messages only when supported; announce
save status politely and errors assertively. A 409 offers Reload current draft with
clear unsaved-change warning, not an implicit overwrite. Unknown network outcome
allows only the identical retry until reconciled. 401/403 clears protected state and
provides safe sign-in/revalidation. Fresh signup is not an expired-proof error.

## Architecture and maintainability

Reuse `FieldHelp`, `TimezonePicker`, existing Admin tokens/button variants and the
existing server-owned `SetupWorkspace` save/revision/request-id logic. Extract a
presentation-only WizardShell, StepNavigation, SaveStatus, FormSection, ErrorSummary,
SelectionCard and sticky WizardActions. Step editors remain domain-specific; do not
create a generic schema-to-form engine or copy the entire Setup state per step.
Use a location summary/editor pattern and reusable list/editor framing for staff and
services. Native disclosures/dialogs, accessible names, focus restoration and keyboard
operation remain first-class. Color choices require actual contrast evaluation.

Start with explicit Save & continue, not automatic sensitive saves. Future autosave
may save valid drafts with debouncing and serialized revision-aware requests; never
race autosave with guide approval, change a completed state implicitly, replay a
changed request under an old idempotency key, or silently publish. Save & exit must
wait for confirmed success or clearly offer leaving unsaved edits. Keep private data
in memory and server drafts, not browser storage. Business changes abort old requests
and clear old private state; ordinary focus revalidation preserves still-authorized
workspace edits. Maintain one Owner-scoped assignment per authorization decision.

The central state machine must map presentation order to backend legal transitions.
Services-before-Team is a UX preference, not permission to reorder server transitions
silently. Use free viewing with validated progress, or separately approve an API/state
migration if ordering must change. Completing backend review requires confirm_review;
there is no implication of actual publication or application of proposed records.

## Implementation sequence — approval gates

1. **Truthful flow and completion:** approve terminology and journey; unify viewed vs
   saved progress, explicit next steps, first-shop reuse, safe Review outcome. Preserve
   ordinary-login boundary and validate final-review API integration before coding.
2. **Wizard shell and forms:** reuse Admin tokens/help, consistent actions and error
   handling; mobile step navigation, unsaved-change protection and focus management.
3. **Simplify editors:** locations conditional fields, staff/access separation, price
   matrix and overrides, visual branding presets. No new domain actions.
4. **Acceptance and polish:** end-to-end new/existing Owner journeys, revision conflicts,
   resume/reload/back, guide compatibility, keyboard/mobile and public booking regression.

Owner decisions needed: approve step order (and its state-machine implications),
identifier wording, optional/deferred-stage language, default collapsed guided help,
and “Finish setup review” as a truthful unpublished outcome. Publishing, invitation
application and mobile capacity remain separate product/security milestones.

## Test and acceptance strategy

Use disposable real-Keycloak users and isolated PostgreSQL fixtures; never conflate
mocked responses with identity/provisioning acceptance. Verify new registration/email,
existing-Owner SSO, atomic tenant/grant/audit creation, named success, normal login and
correct company Setup. Add disabled-registration readiness and browser recovery,
expired proof, competing tabs, duplicate requests, bad slug/timezone, 401/403, revision
collisions and uncertain writes. Some remain gaps in current browser coverage.

Per viewport (1440/768/390), check no document overflow, visible labels/focus, usable
buttons, reachable errors, dialog focus containment/return and readable contrast.
Keyboard-test all steppers, radio cards, dialogs and help disclosures. Test long names,
multiple locations/staff, empty/solo configurations and incomplete matrices. Do not
claim WCAG conformance from screenshots or the existing narrow keyboard assertions.
Assert save/resume and guide approvals preserve tenant, reference and revision rules;
assert no active catalog/employee/role/public-booking changes from draft edits. Preserve
ordinary focus state, business-switch isolation, Admin and anonymous booking tests.

The corrected isolated audit passed **13/13 scenarios**, including real registration,
local email action, verified callback, provisioning success, ordinary login, business
switching, Begin setup, locations, staff, catalog overrides, all branding presets,
guide approval, resume/reload/back and logout. Existing specs supplied keyboard
checks for help disclosures and staff/service choices. This is not an independent
screen-reader audit or comprehensive keyboard/contrast certification. Maximum
captured document height was **3399px**; no captured state exceeded its viewport
width. Responsive containment passes, but that does not make the long forms usable.

The first harness attempt failed to parse capture substitutions and cleaned its
fixtures without screenshots. A partial capture pass then hit existing tests'
implicit prerequisite of an already-created draft; it was interrupted and cleaned.
The corrected pass explicitly performed Begin setup and initial save through the UI.
The partial archive is retained separately; its failures are harness dependencies,
not evidence of a production regression. Temporary specs were removed after capture;
credential-free provenance copies remain in the primary archive's audit-harness folder.

The focused runner cleaned its owned realm, identities, mail, database fixtures and
processes. Full-suite cross-feature fixture-outcome assertions are not run for this
filtered audit. No application suites were rerun as a redesign checkpoint because
no redesign was implemented. Final checks cover documentation links/diff and released
test ports. Owner development login and records were not used or independently
verified. Final completion/publication, invitations, live catalog application, real
mobile capacity and logo uploading cannot be visually accepted as working features;
they remain absent or draft-only as described above.
